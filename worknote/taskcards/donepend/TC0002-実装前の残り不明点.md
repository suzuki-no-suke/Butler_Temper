TC0002 実装前の残り不明点
==========================

# 内容

アプリケーション（チャットボットのプロンプトによる性格表出を調査・調整する道具）を作り始める前に、ユーザーとまだ決めていない点の一覧。
各項目は、この資料だけで読めるように「背景」「決まっていること」「決まっていないこと」「なぜ決める必要があるか」を書く。


# 項目

## A. BOT が複数のモデルを使う場合

- 背景
  - BOT は、プロンプトや実行時パラメーターなどの設定を持つ対話相手。利用者は BOT とチャットし、設定を変えながら応答の違いを調べる
- 決まっていること
  - BOT ごとに利用するモデルを固定する。日付付きのモデル ID があれば必ずそれを使う
  - LLM API（Anthropic / OpenAI など）を切り替えるときは、新しい BOT として作る
  - 同じ LLM API の中でも、モデルは原則変えさせない（2026-10-29 ユーザー回答）
- 決まっていないこと
  - ユーザーは理由として「複数を使うなどの可能性もある」と述べた。一つの BOT が複数のモデルを使う構成（例 : 応答用と要約用で別モデル）を想定しているのかは確認していない
  - ユーザーが以前挙げた「再実行ができないよう強制ガードするべきでは」が、何の再実行を防ぐものかは確認していない
- なぜ決める必要があるか
  - BOT が持つモデルが一つか複数かで、BOT の DB の構造が変わる。最初に作る「チャットと BOT の最低限の会話」にも関わる

## B. 回答へのコメント・評価を付ける単位

- 背景
  - チャット画面では、BOT の回答にコメント・評価を残せる
- 決まっていること
  - 評価は GOOD / FINE / BAD の三段階 + 自由記述
- 決まっていないこと
  - BOT の発言一つずつに付けるのか、会話全体に一つ付けるのか、両方か
  - ユーザー回答に「全体にそうする」という一文があり、Claude はこれを「会話全体にも付ける」とも「すべての回答に同じ形式を使う」とも読めたため、確認が必要と判断した
- なぜ決める必要があるか
  - コメントを紐付ける先（発言か会話か）で DB の構造が変わる

## C. BOT 設定のバージョンをどこに保存するか

- 背景
  - BOT 設定画面には「編集中の設定」があり、利用者が「保存」すると DB に保存され、利用可能なバージョンになる（ユーザー回答）
  - 一方、データ置き場について「public_data（Git にコミットする置き場）には BOT 設定の全バージョンを置く」とユーザーが回答した
  - DB（SQLite）のファイルをどこに置くかは決まっていない
- 決まっていないこと
  - BOT 設定を入れる DB のファイル自体を public_data に置くのか
  - DB には data 側に保存し、それとは別に BOT 設定の全バージョンを JSON などのテキストで public_data に書き出すのか
- なぜ決める必要があるか
  - SQLite のファイルは Git で差分が見えず、コミットのたびに丸ごと変わる。テキストで書き出すなら、書き出しの仕組みが別に要る

## D. data に置くもの

- 背景
  - data は Git にコミットしないデータ置き場、public_data はコミットする置き場
  - ユーザー回答は「data には RAW データ、チャットログの大半。ほかに必要なら原則 data」
- 決まっていないこと
  - 「大半」から外れる、data に置かないチャットログがあるのか、あるなら何か
- なぜ決める必要があるか
  - チャットログの一部を public_data に置くなら、その選び方と書き出しの仕組みが要る

## E. マイグレーションの道具

- 背景
  - DB は SQLite と PostgreSQL の両対応。ORM は SQLModel。マイグレーションは原則 Python スクリプトとし、リモートでは Python で動かす
  - ユーザーは、ローカルでは `npm run migrate` から Python を呼ぶ形が楽と考えている
  - DB は通常の DB と RAW 用の DB の二つがある
- 決まっていないこと
  - Alembic を使うか、自前の Python スクリプトで書くか
- なぜ決める必要があるか
  - 最初の DB を作る時点で、マイグレーションの管理方法が要る
